# P2P 与 CDN（重要性: ★★）

#networking #application-layer #p2p #cdn #concept

## 概览表（一目了然）
| 条目 | 要点 |
|------|------|
| P2P 分发 | 分发时间随 N 增长**亚线性**（peer 也贡献上传） |
| BitTorrent | 256KB 块；tracker；**tit-for-tat** 策略 |
| CDN 策略 | **enter deep**（Akamai）vs **bring home**（Limelight） |
| DASH | 自适应码率流化；manifest 文件 + 客户端智能选择 |

## 文件分发：C/S vs P2P

```
         server(us)
            │
    ┌───────┼───────┐
   peer1   peer2   peerN
   (d1,u1) (d2,u2) (dN,uN)
```

| 模式 | 最小分发时间 |
|------|-------------|
| **Client-Server** | D_c-s > max{**NF/us**, F/d_min} |
| **P2P** | D_P2P > max{F/us, F/d_min, **NF/(us+Σui)**} |

- C/S：服务器需顺序传 **N 份**副本 → 随 N **线性增长**
- P2P：每个节点下载 F bits，总体 NF bits 由 us+Σui 分担 → 分母随 peer 增多而增大

> 课件例题：u=F/u=1h, us=10u, d_min≥us → P2P 分发时间随 N 增长远慢于 C/S。

## BitTorrent

### 核心概念

| 术语 | 含义 |
|------|------|
| **Torrent（洪流）** | 交换文件块的 peer 组 |
| **Tracker** | 跟踪 torrent 中参与节点 |
| **块（chunk）** | 文件分为 **256 KB** 块 |

### 工作流程

```
1. Peer 向 Tracker 注册，获取 peer 列表
2. 与部分 peer 建立邻居关系
3. 下载块的同时向其他 peer 上传
4. 拥有全部块后可自私离开或利他保留
```

### 块请求策略

- 周期性询问邻居拥有哪些块
- 请求时：**稀缺块优先**（rarest first）

### 块发送策略：Tit-for-Tat（一报还一报）

| 规则 | 说明 |
|------|------|
| 常规 | 向提供**最大上传带宽**的 4 个 peer 发送块 |
| 重新评估 | 每 **10 秒**重新评估 top 4 |
| 疏通 | 每 **30 秒**随机选一个 peer 发送块（"optimistic unchoking"） |

→ 更高上传速率 → 发现更好交易伙伴 → 更快传输。

## 视频流化

### 挑战

- 视频占住宅 ISP 流量 ~80%（2020）
- **规模性**：单超级服务器无法服务 ~10 亿用户
- **异构性**：不同带宽/终端/需求

### 编码基础

| 概念 | 说明 |
|------|------|
| 空间冗余 | 图像内压缩（如重复颜色） |
| 时间冗余 | 帧间差分编码 |
| **CBR** | 固定码率 |
| **VBR** | 可变码率 |

### 流化与播放缓冲

```
服务器发送 ──→ [网络延迟变化] ──→ 客户端接收缓冲 ──→ 连续播放
                                  ↑
                            播放缓冲补偿抖动
```

- 连续播放限制：播放时间须与原始时间一致
- 客户端缓存 + **播放延迟**补偿网络抖动

## DASH（Dynamic Adaptive Streaming over HTTP）

```
服务器: 视频分块 → 每块多种码率 → 各 CDN 节点存储 → manifest 文件
客户端: 估计带宽 → 查 manifest → 请求合适码率块 → 自适应切换
```

| 组件 | 功能 |
|------|------|
| **Manifest 文件** | 提供不同视频块 URL |
| **智能客户端** | 决定何时请求、什么码率、从哪个服务器请求 |

Streaming video = **encoding + DASH + playout buffering**

## CDN（Content Distribution Network）

### 为何不用单超级数据中心？

- 单点故障、网络拥塞、路径过长 → **不可扩展**

### 两种部署策略

| 策略 | 做法 | 代表 |
|------|------|------|
| **Enter deep** | CDN 服务器**深入**大量接入网，更接近用户 | **Akamai**（120+ 国家，240,000 服务器） |
| **Bring home** | 在离 ISP POP 较近的**关键位置**部署少量大型服务器簇 | **Limelight** |

### CDN 工作流程

```
1. 用户请求视频 URL（netcinema.com/...）
2. 本地 DNS 解析 → 权威 DNS 返回 CNAME（KingCDN.com/...）
3. 解析 CDN 域名 → 获取最近 CDN 服务器 IP
4. 客户端向 CDN 服务器请求 manifest → DASH 流化
```

- CDN 在节点存储内容**副本**
- 拥塞时可切换不同速率或不同副本
- **OTT**（Over The Top）：在拥塞的 Internet 上从边缘复制内容
