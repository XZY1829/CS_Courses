# 拥塞控制（重要性: ★★★）

#networking #transport-layer #tcp #congestion-control #concept

## 概览表（一目了然）
| 条目 | 要点 |
|------|------|
| 拥塞定义 | 数据量超过网络（非主机）处理能力 |
| vs 流量控制 | 拥塞=多发送方太快；流量控制=单发送方淹没接收方 |
| 检测 | **3 冗余 ACK**=轻微拥塞；**超时**=严重拥塞 |
| 控制变量 | **cwnd**（拥塞窗口）；速率 ≈ cwnd/RTT |
| 策略 | 慢启动(SS) + 拥塞避免(CA) + AIMD + 快恢复 |

## 拥塞控制原理

**拥塞**：太多数据需网络传输，超过网络处理能力。

| 表现 | 说明 |
|------|------|
| 长排队延迟 | 分组在路由器队列中等待 |
| 分组丢失 | 路由器缓冲区溢出 |

### 拥塞 vs 流量控制

| | 拥塞控制 | 流量控制 |
|---|----------|----------|
| **问题** | 太多发送方发送太快 | 一个发送方淹没一个接收方 |
| **范围** | 网络范围 | 端到端（发送方-接收方） |

### 拥塞的代价

- 必要/不必要的**重传**浪费链路容量
- 有效吞吐量低于链路容量 R
- 多跳场景：某流丢包导致上游资源全部浪费

### 拥塞控制方法

| 类型 | 说明 | 例子 |
|------|------|------|
| **端到端** | 主机根据延迟/丢失推测拥塞 | **TCP** |
| **网络辅助** | 路由器提供显式拥塞反馈 | **ECN**、ATM、DECbit |

## TCP 拥塞控制机制

**SendWindow = min{cwnd, RcvWin}**

**速率控制**：
\[
\text{LastByteSent} - \text{LastByteAcked} \leq \text{cwnd}
\]
\[
\text{rate} \approx \frac{\text{cwnd}}{\text{RTT}}\ \text{bytes/sec}
\]

### 三个核心问题

| # | 问题 | 答案 |
|---|------|------|
| 1 | 如何检测拥塞？ | **3 冗余 ACK**（轻微）或 **超时**（严重） |
| 2 | 如何控速？ | 调节 **cwnd** |
| 3 | 控制策略？ | **负反馈**：拥塞降速，无拥塞增速 |

### 状态与控制策略

| 状态 | 正常 ACK | 3 冗余 ACK | 超时 |
|------|----------|------------|------|
| **慢启动 SS** | cwnd += MSS（每 ACK）；每 RTT **加倍** | ssthresh=cwnd/2；cwnd=ssthresh+3；**快恢复** | ssthresh=cwnd/2；**cwnd=1**；回 SS |
| **拥塞避免 CA** | cwnd += MSS/cwnd（每 ACK）；每 RTT **+1 MSS** | 同上 | ssthresh=cwnd/2；**cwnd=1**；回 SS |

**慢启动 (Slow Start)**：
- 连接初始 cwnd = **1 MSS**
- 每收到 ACK → cwnd += MSS（每 RTT **指数增**）
- 直到 cwnd > ssthresh 或发生丢失 → 转 CA

**拥塞避免 (Congestion Avoidance)**：
- cwnd ≥ ssthresh 时进入
- 每 RTT **线性增 1 MSS**（加性增）

**AIMD**（Additive Increase, Multiplicative Decrease）：
- **加性增**：每个 RTT 增加 1 MSS 直到探测到丢失
- **乘性减**：丢失时减半（Reno）或降至 1 MSS（Tahoe）

### SS → CA 切换

当 **cwnd ≥ ssthresh** 时从指数增切换为线性增。ssthresh 在丢失时设为丢失前 cwnd 的**一半**。

## TCP Tahoe vs Reno vs CUBIC

| 变体 | 3 冗余 ACK | 超时 |
|------|------------|------|
| **Tahoe** | cwnd 减半 | cwnd → **1 MSS**，慢启动 |
| **Reno** | cwnd → **cwnd/2 + 3**，快恢复 | cwnd → **1 MSS**，慢启动 |
| **CUBIC** | 基于 **Wmax** 的立方函数调节 cwnd；Linux 默认 | 类似 Reno |

**CUBIC 直觉**：
- Wmax = 检测到拥塞丢失时的窗口
- 丢失后先快速增到 Wmax 附近，再缓慢接近 Wmax
- 窗口增量 W = cube(K-t)，K 为到达 Wmax 的时间点

## 公平性分析

**公平性目标**：K 个 TCP 连接共享带宽 R 的瓶颈链路，各得 **R/K**。

在理想假设下（相同 RTT、固定会话数、仅 CA 阶段），AIMD 使连接公平共享带宽。

| 不公平因素 | 说明 |
|------------|------|
| **UDP** | 无拥塞控制，占用更多带宽 |
| **并行 TCP 连接** | 浏览器开 11 条连接可得 R/2（9 条已有连接时） |

**平均 TCP 吞吐量**（忽略慢启动，W 为丢失时窗口）：
\[
\text{avg throughput} = \frac{3}{4} \times \frac{W}{\text{RTT}}\ \text{bytes/sec}
\]

**长肥管道**（Mathis 公式）：
\[
\text{TCP throughput} \approx \frac{1.22 \times \text{MSS}}{\text{RTT} \times \sqrt{L}}
\]
L = 段丢失率

## ECN（显式拥塞通知）

TCP 常实现网络辅助拥塞控制：

```
路由器: IP 头部 ToS 中 ECN 位标记 (10→11)
接收方: TCP ACK 段设 ECE=1 通告发送端
发送端: 收到 ECE → 降 cwnd（同 3 冗余 ACK）
```

涉及 **IP 头部 ECN 标志** + **TCP 头部 C/E 位**。

### 瓶颈链路洞察

- TCP 增速率直到某路由器输出口丢包 → **瓶颈链路**
- 增发送速率**不增**端到端吞吐，但**增** RTT
- 目标：管道"满但不太满"

> [!warning]
> 超时可能由**拥塞丢包**（大概率）或**比特差错丢包**（小概率）引起；TCP 一律视为拥塞，存在误判但方向正确。

## 考试/测试常见模式
| 场景/关键词 | 答案 |
|-------------|------|
| "拥塞 vs 流量控制" | 拥塞=网络过载；流量控制=接收方缓冲 |
| "轻微/严重拥塞信号" | **3 冗余 ACK** / **超时** |
| "慢启动 cwnd 增长" | 每 RTT **加倍**（每 ACK +MSS） |
| "拥塞避免 cwnd 增长" | 每 RTT **+1 MSS**（线性） |
| "Reno 3 冗余 ACK" | cwnd → **ssthresh + 3**，快恢复 |
| "Tahoe 超时" | cwnd → **1 MSS** |
| "SendWindow" | **min(cwnd, RcvWin)** |
| "ECN 流程" | 路由器标记 IP → 接收方 ECE → 发送方降 cwnd |
