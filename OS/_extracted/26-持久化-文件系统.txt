硬链接（Hard Link）
•
将⼀个新的⽂件名link 到目标文件的inode
•
两个不同的⽂件名指向磁盘中存储的同⼀个⽂件
•

硬链接（Hard Link）
• 对应地，使⽤unlink() 来删除⼀个⽂件
• ⽂件系统为每个inode 记录⼀个reference count (link counter) 
• 在每次unlink() 时对该count 值减⼀
• 直到count值等于0，文件系统才会释放inode和相关磁盘数据块，删除文件
硬链接（Hard Link）
• 不能跨⽂件系统创建Hard Link 
• inode号在特定文件系统中是唯一的，而不是跨文件系统
• 为了简化管理，通常不允许创建⽬录⽂件的Hard Link 
• 避免在⽬录层次结构中引⼊环(同⼀个⽂件有⽆数的path names) 
• 破坏⽗⽬录的唯⼀性(如果多个⽗⽬录都指向同⼀个⼦⽬录的链接，则该⼦⽬
录的‘..’⽬录项应指向哪个⽬录？)
符号链接（Symbolic Link）
•
创建⼀个链接类型的新⽂件（文件、目录以外的第三种），有时也称为软链接
• 该符号链接⽂件中存储目标文件的路径名(path name)
•
创建符号链接：ln -s a.txt b.txt
符号链接（Symbolic Link）
• 与硬链接不同：能link 到不同的⽂件系统、或⽬录⽂件
• 在打开⽂件时需要额外解析符号链接
• 读取符号链接⽂件中存储的目标文件的路径，使⽤该路径打开
• 但目标文件可能也是⼀个符号链接⽂件
• 当删除⼀个符号链接⽂件时，不影响目标文件
• 当删除目标文件时，可能会造成悬空引用（dangling reference）
• 符号链接指向的⽂件不存在

•
每个⽂件占据⼀个连续的数据块集合
‣ ⽐如对于磁盘数据块⼤⼩为1KB的情况, ⼀个20KB的⽂件就是占据了20个连
续的数据块
⽂件组织：连续分配
每个⽂件实现为磁盘上的若⼲连续data blocks：
• 仅需在⽂件属性中记录first block + total number of 
blocks 信息
• 优点：有较好的顺序读写性能、且能快速定位数据块
• 缺点：
• 但显然不够灵活，在创建⽂件时需确定⽂件⼤⼩
• 还会存在严重的外部碎⽚问题
• 在特定场景下仍是很好的选择(e.g., 静态文件存储)
⽂件组织：链表方式(Linked Allocation)
每个⽂件实现为data blocks 的⼀个链表：
• 仅需在⽂件属性中记录首个数据块信息
• 可以把所有数据块都利⽤起来(没有外部碎⽚)
• ⽐较适合⼩⽂件，但是
• 性能较差：定位⼀个⼤⽂件的随机数据块需要
遍历链表
• 存储开销增大：每个数据块中需要额外存储⼀
个指针
• 可靠性问题：指针损坏导致⽂件丢失
文件分配表（File Allocation Table, FAT）
将数据块链表中的所有指针集中存放到⼀个File 
Allocation Table (FAT) 中，更高效地支持随机访问
• 每个数据块对应FAT 中的⼀个表项，其存储
• ⽂件下⼀个data block 的编号
• ⽂件终⽌标记
• 空闲空间标记
• 此时定位⽂件的随机数据块只需访问FAT结构(可缓
存在内存)

FAT ⽂件系统的磁盘布局
• 保留扇区位于磁盘起始位置，包含引导扇区

文件分配表（续）
•
FAT 是⼀个设计和实现较为简单的⽂件系统，⼴泛应⽤于许多便携和嵌⼊式设备
(早期Windows, DOS, USB等) 
• 但在内存中缓存整个FAT 结构会导致较⾼的存储开销

• 如果每个表项占⽤4 bytes (FAT 32)，则整个FAT 表⼤⼩为1GB

空闲空间管理
•
如何管理空闲的inode块和数据块？
‣ 每当⽂件和⽬录需要被创建的时候需要找到空闲的空间存储这些数据
‣ 两种常⻅的管理结构：Bitmap（位图）和空闲列表
‣ 也有采⽤更复杂结构如B树
空闲空间管理：Bitmap
•
每个数据块⽤⼀个bit位来表达，0和1代表占据或者空闲
•
很容易找到连续的空闲空间
•
Bitmap需要额外的空间
•
Block size = 4 KB = 212 bytes 
•
Disk size = 1 TB = 240 bytes 
•
需要240 / 212 = 228 bits = 32 MB空间的位图
1TB磁盘空间仅需32MB位图空间
空闲空间管理：空闲列表
• ⽤⼀个链表来维护空闲块
• 没有空间浪费，只需要利⽤空闲空间块来存储指针
即可
• 内存中只需要存储⼀个指针（head）
• 但分配的效率⽐较低：
• 需要搜索这个链表来分配多个空闲块(需要额外
的磁盘I/O) 
• 难以得到连续的空间
• 不支持并发优化

文件系统的性能
•
每次对磁盘数据块的read 和write 都是磁盘I/O 操作(⽐直接读写内存要慢很多)，
需要尽量降低这些操作的开销
• 考虑局部性（空间和时间）
• Caching and Buffering 
• 考虑存储介质(如磁盘) 的特点
• 快速文件系统（Fast File System, FFS）
• 日志结构的文件系统（Log-Structured File System, LFS）*
Caching and Buffering：caching
•
将频繁访问的数据缓存在内存中(caching) 
• 例如，对于⽂件的存储位置信息
• FAT 将所有数据块的pointer 缓存在内存中
• Unix 打开⽂件表中缓存了当前已打开⽂件的inode 数据
• 缓存区满时需要考虑替换策略
• 相⽐于物理⻚⾯替换，可以在⽂件系统中维护精确的LRU 信息(⽂件系统是
纯软件实现的系统，且涉及I/O 操作) 
• 可以通过预取(pre-fetching) 技术来在I/O 空闲时提前读取数据
• 尤其在顺序访问⽂件时⾮常有效
Caching and Buffering: write buffering
•
将需要写回磁盘的数据先暂存在内存缓冲区中(delay writes) 
• Write-through Policy: 修改后⽴即写回
• 可能导致磁盘的⼤量随机写操作
• ⽽且有些写操作是可以避免的(e.g., create a file and then delete it) 
• Write-back Policy: 修改后仅标记为dirty 并延迟写回
• 在超过⼀定时间间隔、缓冲区满、关闭⽂件、或显式调⽤flush()时才
写回磁盘
• 以牺牲潜在⼀致性的代价来提⾼性能
• 系统奔溃时丢失尚未写回的数据
文件系统的性能问题
•
在设计⽂件系统布局(file system layout) 时考虑存储介质的物理特性
• 之前考虑的⽂件系统布局其实把磁盘看作了⼀种random access 存储介质
• 所有inodes 放在磁盘开始的⼀段空间中
• 任意空闲的data block 都可⽤于分配
• 在⽂件操作时会导致太多的磁头移动(disk arm motion) 开销
快速文件系统：组织结构
•
FFS 将整个磁盘分为若⼲block groups (Berkeley, 1984) 
• 每个group 有各⾃allocation structure、inode table 和data region
快速文件系统：如何分配文件和目录
•
FFS 将整个磁盘分为若⼲block groups (Berkeley, 1984) 
• 每个group 有各⾃allocation structure、inode table 和data region
• 将可能依次访问的相关数据放在相邻位置
• 在创建⽂件时：
• 同⼀⽂件的inode 和data 放在同⼀个group 
• 同⼀⽬录下的⽂件放在同⼀个group 
• 在创建⽬录时：均衡目录分布
• 找⼀个已存储⽬录相对较少，且空闲inode 相对较多的group 
• 还可以通过碎⽚整理(defragmenting) 来把数据放到⼀起
文件系统的性能问题
•
在设计⽂件系统布局(file system layout) 时考虑存储介质的物理特性
• 硬件的发展带来更快的CPU 和更⼤的内存
• 可以通过缓存来加速对磁盘的读操作
• 性能瓶颈主要集中于对磁盘的写操作
• 随机写磁盘数据块性能很差
• 尝试把很多⼩的随机写变成⼀个⻓的顺序写（写缓冲、写日志、FFS
块组设计）
