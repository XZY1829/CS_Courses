## 排序算法

| 算法 | 最好时间 | 平均时间 | 最坏时间 | 额外空间 | 稳定 | 原地 | 特性与取舍 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 直接插入排序 | O(n) | O(n²) | O(n²) | O(1) | 是 | 是 | 小规模或基本有序时很好；元素搬移较多 |
| 折半插入排序 | O(n log n) | O(n²) | O(n²) | O(1) | 是 | 是 | 折半只把比较次数降到 O(n log n)，元素移动仍是 O(n²) |
| 希尔排序 | 取决于 gap | 取决于 gap | 常见 gap 下 O(n²) | O(1) | 否 | 是 | 插入排序的分组改进；性能依赖增量序列，不适合要求稳定排序的场景 |
| 冒泡排序 | O(n) | O(n²) | O(n²) | O(1) | 是 | 是 | 加提前退出后可利用已有序性；交换次数多，工程中较少使用 |
| 快速排序 | O(n log n) | O(n log n) | O(n²) | 平均 O(log n)，最坏 O(n) | 否 | 通常是 | 缓存友好、常数小；基准选择差或划分极不均衡时会退化 |
| 直接选择排序 | O(n²) | O(n²) | O(n²) | O(1) | 否 | 是 | 比较次数固定，但交换次数少；适合写操作昂贵且数据量小的场景 |
| 堆排序 | O(n log n) | O(n log n) | O(n log n) | O(1) | 否 | 是 | 最坏复杂度有保证、空间小；缓存局部性和常数通常不如快排 |
| 归并排序 | O(n log n) | O(n log n) | O(n log n) | 数组 O(n) | 是 | 否 | 性能稳定，适合链表、外部排序和需要稳定性的场景；数组合并需辅助空间 |
| 桶排序 | O(n+k) | O(n+k) | O(n²) | O(n+k) | 取决于桶内排序 | 否 | 非比较排序；数据分布均匀、值域可映射时接近线性，分布失衡会退化 |
| Introsort | O(n log n) | O(n log n) | O(n log n) | O(log n) | 否 | 通常是 | 快排为主，递归过深切堆排，小区间切插入排序；兼顾平均性能和最坏保证 |

- 稳定性：相等元素排序后的相对顺序不变。直接插入、冒泡、归并通常稳定；快排、选择、堆排、希尔通常不稳定。
- 原地排序：额外空间为 O(1) 或只使用递归栈，不需要与输入规模同量级的辅助数组。
- 快排退化：划分持续极不均衡时，递归树退化，时间 O(n²)、栈空间 O(n)。可用随机基准、三数取中和三路划分降低风险。
- 为什么 `std::sort` 常采用 Introsort：快排平均快但无最坏保证；达到递归深度阈值后切到堆排序，将最坏时间兜到 O(n log n)，小区间再用插入排序降低常数。
- 堆排序：自底向上建堆是 O(n)，从最后一个非叶子节点 `n / 2 - 1` 开始调整；随后每次把堆顶最大值交换到数组末尾并重新调整堆。
- 归并排序：核心是用双指针合并两个有序区间；数组版需要 O(n) 临时空间，链表版可通过改指针降低额外空间。

## 哈希与搜索结构

- 哈希函数设计
- 冲突解决：链地址法每个桶存一个链表
- 开放寻址法 冲突时寻找下一个空位置
- 1 线性探测h(key) + i
- 2 二次探测h(key) + i²
- 3 双重哈希index = h1(key) + i * h2(key)
- 哈希冲突面试不要只背名字：拉链法删除简单但节点分散、缓存局部性差；开放寻址缓存友好但删除要 tombstone，负载因子高时探测成本明显上升
- 工程上还要说负载因子、扩容 rehash、哈希函数质量；unordered_map 扩容后迭代器可能失效，不要长期保存桶内元素地址
- 如果状态空间固定、稠密、可枚举，数组/direct addressing 常比哈希更合适。例：2048 一行 4 格，每格 5 bit，一行 `2^20` 种，数组查表稳定 O(1)、连续内存、缓存友好
- 搜索结构
- 大小端存储0x12345678 4字节整数
- 大端：地址低 → 高位字节 和人类读数字顺序一致 12 34 56 78
- 好处：读取数字更直观网络协议通常使用（历史原因互联网早期很多主机使用大端架构）
- 小段：地址低 → 低位字节 78 56 34 12
- 好处：CPU计算更方便 最低位就在最低地址，加法、进位等运算效率更高
- 网络协议和跨平台二进制文件不要直接裸发 C++ struct：端序、padding、字段版本都会坑；协议层明确字段大小和字节序

## C++ 对象、引用与移动语义

- 内存对齐：不是为了方便 `sizeof`，而是硬件访问效率和 ABI 约定；每个成员放到满足自己对齐要求的位置，结构体整体大小补齐到最大对齐值的倍数，保证结构体数组里的下一个元素也继续对齐
- 结构体对齐例子：`char + int + short` 通常是 12；调整成 `int + short + char` 通常是 8。先算 offset，再报 `sizeof`，别凭感觉
- A a, A& a, A&& a?
- 1.A a —— 普通对象（值）会 创建一个对象;拥有自己的内存;生命周期独立
- 2.A& a —— 左值引用必须绑定到 左值（有名字的对象）;相当于 别名（alias）;不会创建新对象
- 3.A&& a —— 右值引用（C++11）绑定到 右值（临时对象）;用于 移动语义 / 完美转发;可以“接管资源”
- 左值核心是有身份、通常可取地址；右值通常是临时值或即将被移动的值；`const T&` 可以绑定临时对象并延长生命周期
- std::vector<int> v3 = std::move(v1);不拷贝数据，而是：直接“拿走” v1 的内部指针;v1 变空
- 本质：资源转移，而不是复制
- 移动构造
- A(A&& other) {
- data = other.data; // 偷资源
- other.data = nullptr; // 防止双重释放
- }
- 移动语义是通过右值引用实现的，其核心是将资源从一个对象“转移”到另一个对象，从而避免不必要的深拷贝，提高性能。std::move 本质是类型转换（static_cast<A&&>(a)），不会真正移动数据。真正的移动发生在移动构造或移动赋值中。A&& a = A();中a是左值。
- moved-from 对象仍然有效，但值只保证可析构、可赋值，不要继续依赖原内容；返回局部变量通常直接 `return obj;`，不要机械 `return std::move(obj);`，可能影响 RVO
- 完美转发：template<typename T>
- void f(T&& t);这里的 T&&：不是普通右值引用，而是 万能引用（转发引用）传左值 → 变成 T&；传右值 → 变成 T&&
- std::forward<T>(t)
- 引用折叠口诀：只要出现一个 `&`，最后就是左值引用；只有 `T&& &&` 才折叠成右值引用
- 移动构造：当连续内存不足时，vector 会重新申请一块更大的连续空间，并将原有元素移动（或拷贝）过去，而不是在原地扩容。
- vector 扩容后旧迭代器、指针、引用失效，根因是连续内存被重新分配；知道数量先 `reserve`，需要稳定地址就考虑索引、deque/list、对象池等

## 进程内存布局、函数调用与栈帧

| 区域 | 典型内容 | 生命周期与线程关系 |
| --- | --- | --- |
| `.text` 代码段 | 编译后的函数机器指令 | 进程内线程共享，通常只读、可执行；函数代码本身不在调用栈里 |
| `.rodata` 只读数据 | 字符串字面量、部分只读常量 | 进程生命周期，线程共享 |
| `.data` 数据段 | 已初始化且可修改的全局变量、静态变量 | 静态存储期，线程共享 |
| `.bss` | 未显式初始化或零初始化的全局变量、静态变量 | 静态存储期，线程共享；可执行文件不必保存大段零值 |
| 堆 | `new` / `malloc` 分配的动态对象 | 进程共享，生命周期由程序或所有权系统管理，并发访问要同步 |
| 栈 | 返回地址、保存的寄存器、部分参数、局部变量、临时空间 | 每个线程独立；一次函数调用对应一个栈帧，返回后回收 |
| TLS | `thread_local` 对象 | 每个线程各有一份，不等同于普通全局/静态变量 |

- 上表是简化的虚拟地址空间模型，具体地址受 OS、链接器和 ASLR 影响；“堆向高地址、栈向低地址”是示意，不要理解成所有系统都连续这样增长。
- 静态存储区是存储期概念，不是唯一的物理段；对象可能落在 `.data`、`.bss` 或 `.rodata`。局部 `static` 也不在普通函数栈帧中。
- x86/x64 栈通常从高地址向低地址增长。32 位下 `push eax` 近似 `sub esp, 4; mov [esp], eax`；弹栈则读取后增加 `esp`。
- `ESP` / `RSP` 是 32/64 位栈顶指针，会随压栈、弹栈和局部空间分配变化；`EBP` / `RBP` 可作为稳定的栈帧基址，但优化编译常省略帧指针。

经典 32 位 x86 `cdecl` 栈帧，假设调用 `add(a, b)`，参数从右向左压栈：

```text
高地址
[EBP + 12] 参数 b
[EBP + 8 ] 参数 a
[EBP + 4 ] 返回地址：call 后下一条机器指令的虚拟地址
[EBP     ] 调用者旧 EBP
[EBP - 4 ] 局部变量/填充
[EBP - 8 ] 局部变量/保存区
低地址                                      <- ESP 位于当前栈顶附近
```

- `call target`：CPU 保存 `call` 执行完后 `EIP/RIP` 应继续执行的地址，再跳到 `target`。例如 `call` 位于 `0x401000` 且指令长 5 字节，返回地址就是 `0x401005`，不是 C++ 的“下一行行号”。
- 典型函数序言：`push ebp; mov ebp, esp; sub esp, N`，依次保存旧基址、建立当前栈帧、给局部变量和临时空间留位置。
- 函数可用固定偏移访问参数和局部变量，根因是 ABI 与编译器已经确定栈帧布局，`EBP` 又保持稳定；内存对齐会加入 padding、改变具体 offset，但不是“能够固定偏移访问”的根本原因。
- 对齐要求同时影响对象布局和栈布局；ABI 常要求调用边界满足特定栈对齐，便于 SIMD 指令和高效访存。编译器负责把变量大小、寄存器保存、padding 一并算进 offset。
- 典型函数尾声：先按逆序析构 C++ 局部对象，再执行 `mov esp, ebp; pop ebp; ret`。移动 `ESP` 只是宣布栈空间可复用，不会清零内存，也不能替代对象析构。
- `ESP = EBP + 4` 不是恒等式：`mov esp, ebp` 后二者相等；随后 `pop ebp` 让 `ESP` 相对刚才的帧基址增加 4、指向返回地址，但此时 `EBP` 已恢复为调用者的旧值；`ret` 再弹出返回地址。
- 经典 `cdecl` 通常由调用者执行 `add esp, 参数字节数` 清理栈参数；其他调用约定可能由被调用者清理，必须以目标 ABI 为准。
- 现代 x64 通常优先用寄存器传参，不是所有参数都压栈。Windows x64 前四个整数/指针参数通常用 `RCX/RDX/R8/R9`，其余参数和溢出值才落栈，调用者还会预留 shadow space。
- 小整数和指针返回值通常放 `EAX/RAX`，浮点值常放 `XMM0`；大对象可能由调用者传入隐藏的返回地址，函数直接在目标位置构造，RVO/NRVO 还能消除复制或移动。
- 完整调用链：准备实参 -> 按 ABI 放寄存器/栈 -> `call` 保存返回地址 -> 保存必要寄存器并建栈帧 -> 执行 -> 放置返回值 -> 析构局部对象 -> 恢复栈帧/寄存器 -> `ret` -> 调用者继续执行。

- 多线程：函数机器码、全局/静态变量和堆属于进程共享；每个线程有自己的寄存器、调用栈和 TLS。同一函数可被多个线程同时执行，每次调用的参数和普通局部变量落在各自线程的栈帧里，彼此可见性问题主要发生在共享数据上。
- C++20 无栈协程：挂起后仍需保存的局部变量、状态和恢复点位于协程帧，通常在堆上，也可能被编译器消除分配；恢复时仍使用当前执行线程的普通栈，且协程可能换线程恢复，依赖 TLS 时要小心。
- 有栈协程拥有独立调用栈，切换时需要保存/恢复栈指针和寄存器上下文；不要把它和 C++20 默认的无栈协程混为一谈。

- 真正的函数内联是在编译期把函数体合入调用点，因此没有这个被调用函数独立的 `call/ret`、返回地址、ABI 参数搬运和栈帧建立/回收；返回值可直接成为调用点表达式，方便继续常量传播、死代码删除和寄存器优化。
- “内联省去参数压栈”是教材化表述：x64 原本就常用寄存器传参；内联后的局部变量仍可能占调用者栈，寄存器不足仍会 spill，C++ 析构语义也不能省。
- `inline` 关键字不保证编译器真正内联；普通函数也可能被优化器内联。它在现代 C++ 中更重要的语言作用，是允许一致的函数定义出现在多个翻译单元中以满足 ODR。
- 内联不是越多越快：复制函数体会增加代码体积并可能降低指令缓存命中率；实际收益通常来自后续跨函数优化，而不只是省几条调用指令。

## 同步调用、异步调用与回调

| 概念 | 调用返回时任务状态 | 调用方如何拿结果 | 核心判断 |
| --- | --- | --- | --- |
| 同步调用 | 通常已经完成 | 返回值、输出参数或异常 | 调用方逻辑上等完成后再继续 |
| 异步调用 | 通常只是已提交/已启动 | callback、future/promise、事件、消息、协程 | 调用方先继续，完成结果以后交付 |
| 回调 | 可能已完成，也可能尚未完成 | 对方在约定时机反过来调用函数 | 它是通知/扩展机制，不天然等于异步 |

```text
同步：调用 -> 当前调用栈等待任务完成 -> 返回最终结果 -> 继续
异步：发起任务 -> 立即返回句柄/started -> 做其他事 -> 未来收到完成通知
回调：把函数交给对方 -> 对方在约定条件满足时调用；可同步，也可异步
```

- 同步调用保持自然的嵌套调用栈：`main -> request -> readFile`；被调用函数返回后栈帧回收，结果通过寄存器、返回对象或异常交给上一层
- 异步函数返回时，发起函数的普通栈帧可能已经销毁；异步完成后，调度器会在当前执行线程上建立一条新的调用栈来执行 callback，不是跳回已销毁的旧栈帧
- `status="started"`、请求 ID、任务句柄只证明请求被接受，不证明最终完成；完成判据要看新鲜且目标匹配的结果、终态事件、可读取产物或完成回调
- 回调不等于异步：`std::sort` 的比较器是回调，但会在 `sort` 返回前同步执行；下载完成回调则通常是异步回调
- 异步也不等于多线程：工作线程可以并行执行任务，单线程事件循环也可以依靠 OS I/O 完成通知实现异步。异步描述控制流，并发描述任务交错推进，并行才是同一时刻真正执行
- 同步不完全等于阻塞：非阻塞 `recv` 可以同步返回 `would block`；异步接口则会登记操作，并在未来通知最终完成
- 异步捕获生命周期：`[&local]` 在原函数返回后可能悬空，简单值用 `[local]` 按值捕获；共享状态可用明确所有权，但不要为了省事滥用 `shared_ptr`
- 捕获裸 `this` 要确认对象活到回调结束；否则使用取消令牌、弱引用或由任务拥有状态。回调还必须明确在哪个线程执行，后台回调不要直接修改只能由主线程操作的 UI/场景对象
- 回调契约要问清：调用零次/一次/多次，成功失败是否都触发，是否可能在注册函数返回前同步触发，取消后是否还有迟到回调，顺序和执行线程是否保证
- `future` 是未来结果的共享状态容器，`get()` 取得结果时可能等待；C++20 `co_await` 把“注册后续操作 + 挂起 + 恢复”写成顺序代码，但底层仍要有完成通知和保存状态的协程帧

- 面试 30 秒版：同步调用返回时结果已经确定，调用方逻辑上等待完成；异步调用只发起任务，最终结果以后通过回调、future、事件或协程交付。回调只是把后续处理函数交给对方调用，既可同步也可异步。异步不等于多线程，工程上重点关注生命周期、执行线程、错误/取消路径和真正的完成判据

## 继承、虚函数与虚继承

- 单继承对齐算例：`Base` 有一个虚函数和一个 `int`，`Derived` 再有一个 `int`

```cpp
class Base {
public:
    virtual void f();
    int baseValue;
};

class Derived : public Base {
public:
    void f() override;
    int derivedValue;
};
```

- 64 位常见布局：`Base` 内有 8 字节隐藏 `vptr`、4 字节 `baseValue`、4 字节尾部 padding，所以通常 `alignof(Base) == 8`、`sizeof(Base) == 16`。虚表本身位于只读数据区，对象里只存指向虚表的 `vptr`
- 简单单继承中 `Derived` 通常复用基类已有的 `vptr`；重写虚函数只是让虚表槽位指向 `Derived::f`，不会每继承一层就增加一个 `vptr`

```text
Base 典型布局
offset 0~7    vptr
offset 8~11   baseValue
offset 12~15  tail padding

Derived 逻辑组成
[Base 子对象：vptr + baseValue + 可能的 tail padding]
[Derived::derivedValue]
[为整体 8 字节对齐补的 padding]
```

- MSVC x64 常见结果：把完整 16 字节 `Base` 子对象放在前面，`derivedValue` 位于 offset 16，再把整体补齐到 8 的倍数，所以 `sizeof(Derived)` 常见为 24
- GCC/Clang 在 Linux x86-64 常采用 Itanium C++ ABI，可能复用非平凡基类的尾部 padding，把 `derivedValue` 放在 offset 12，因此 `sizeof(Derived)` 可能仍为 16；Windows 上的 MinGW g++ 通常采用 Microsoft ABI，不能只按编译器名字判断
- 这个差异说明：派生类整体对齐通常取基类子对象、成员和隐藏字段中的最大对齐，但基类 tail padding 是否复用属于 ABI 实现细节；涉及二进制接口时必须在目标编译器上用 `sizeof`、`alignof` 和实际地址差验证
- `Base* p = &derived; p->f()` 的典型过程：从对象开头读取 `vptr`，再从虚表槽位读取函数地址并间接调用 `Derived::f`；简单单继承的 Base 子对象通常位于 offset 0，不需要调整 `this`，多继承/虚继承则可能需要
- 不要对这种带虚函数和继承的非标准布局类型依赖 `offsetof`；精确布局不是 C++ 标准保证

- 虚继承
- 虚继承用于解决多继承条件下的菱形继承问题（浪费存储空间、存在二义性）。
- 底层实现与编译器 ABI 有关：MSVC 常通过对象内的 `vbptr` 和只读区的 `vbtable` 记录虚基类偏移，`vbptr` 占一个指针大小（32 位常见 4 字节，64 位常见 8 字节）；GCC/Clang 的 Itanium ABI 通常把虚基类偏移信息放进相关虚表结构，不能统一说每个虚继承子类都一定额外有一个 `vbptr`
- 实际上，vbptr 指的是虚基类表指针（virtual base table pointer），该指针指向了一个虚基类表（virtual table），虚表中记录了虚基类与本类的偏移地址；通过偏移地址，这样就找到了虚基类成员，而虚继承也不用像普通多继承那样维持着公共基类（虚基类）的两份同样的拷贝，节省了存储空间。
- 多态基类如果可能通过基类指针删除派生对象，析构函数要 virtual；析构顺序是先派生类，再基类
- 构造/析构函数里调用 virtual 不会按最派生类动态绑定，而是按当前构造/析构层级解析；不要在基类构造里依赖派生类重写逻辑
- 虚函数可以 inline；但通过 Base* / Base& 动态分派时能不能内联取决于编译器能否去虚化。限定名调用 `d.Base::f()` 会压制虚分派
- 空类大小通常是 1，为了保证不同对象有唯一地址；有 virtual 通常会有 vptr，大小至少是一个指针再考虑对齐

## C++ 智能指针、const 与类型转换

- `unique_ptr` 表示独占所有权，不能拷贝只能移动；默认优先用它表达清晰生命周期
- `shared_ptr` 表示共享所有权，有引用计数开销和循环引用风险；只有生命周期确实需要多个 owner 延长时才用
- `weak_ptr` 是观察关系，不增加引用计数；使用前 `lock()`，判断返回的 `shared_ptr` 是否为空
- 循环引用的核心是引用计数降不到 0；常见设计是父拥有子，子反向观察父，不要双方都用 `shared_ptr`
- RAII：资源跟对象生命周期绑定，构造获取资源，析构释放资源；普通模块对象适合独占指针/UPtr，进入引擎对象系统的对象可能由 ObjPtr/GC 扫描管理，别把 ObjPtr 说成 shared_ptr
- `const` 的工程价值是把只读契约写进类型系统：参数用 `const T&` 避免拷贝并表达不修改，成员函数 `const` 表示不修改逻辑状态；`const` 不是线程安全
- `mutable` 有两个常见用法：
  - 修饰数据成员：允许 `const` 成员函数修改该成员，常用于缓存、延迟计算或统计字段；它不等于可以修改所有对象状态。
  - 修饰 Lambda：允许 Lambda 修改按值捕获的内部副本，不会修改外部原变量。例如 `int x = 1; auto f = [x]() mutable { ++x; }; f();` 执行后外部 `x` 仍然是 `1`。
- 四种 cast：`static_cast` 正常类型转换；`dynamic_cast` 多态体系运行时安全下转；`const_cast` 只改 const/volatile 限定，不能安全改写本来就是 const 的对象；`reinterpret_cast` 按比特重新解释，最危险

## C++ 原子操作与内存顺序（memory_order）

### 1. 原子性和同步是两个问题

以 C++11/14/17 的常用规则为学习范围。memory_order 是传给原子操作的顺序选项，用来规定该操作需要提供怎样的线程间排序和同步保证，不是修改变量本身的类型。

- 原子性：一次原子操作作为不可分割的操作参与并发。例如 fetch_add 将读、加、写合为一次原子读改写；两个线程分别执行一次，初值 0 的计数最终为 2（线程完成后观察）。
- 同步：线程 A 写入普通数据后，线程 B 在什么条件下可以安全读取这些数据。对标志位使用 atomic，不代表它旁边的数据自动受到保护。
- atomic 的 load 和 store 即使各自是原子的，先 load 再 store 仍是两个操作，组合起来可能丢失更新；即使用默认 seq_cst 也不会自动合成事务。

```cpp
std::atomic<int> count{0};

// 两个线程并发执行：可能都读到 0，最后都写入 1。
int old = count.load();
count.store(old + 1);

// 需要不可分割的计数更新时：
count.fetch_add(1, std::memory_order_relaxed);
```

### 2. 从一次性数据发布理解 release/acquire

下面是可独立运行的完整示例。数据只发布一次，发布后生产者不再修改 data，变量的生命周期覆盖两个线程。

```cpp
#include <atomic>
#include <iostream>
#include <thread>

int main() {
    int data = 0;
    std::atomic<bool> ready{false};

    std::thread producer([&] {
        data = 42;
        ready.store(true, std::memory_order_release);
    });

    std::thread consumer([&] {
        while (!ready.load(std::memory_order_acquire)) {
            std::this_thread::yield();
        }
        std::cout << data << '\n';
    });

    producer.join();
    consumer.join();
}
```

消费者读到已发布的 true 并继续执行时，输出保证为 42。这里是讲解机制的自旋示例，长时间等待通常应考虑条件变量等阻塞机制；本节未编译运行示例。

release 是“发布”：将该线程在这次操作之前完成的写入纳入可被接收方同步获取的范围。

acquire 是“接收”：当这次 acquire 读取到同一原子变量上对应 release 写入的值时，两次操作建立 synchronizes-with 关系。此例只有一次 true 的写入，所以读到 true 就能确定对应这次发布。更复杂的规则还涉及 release sequence，本轮先限定为直接读到发布值。

```text
生产者线程                              消费者线程
data = 42                               等待 ready
    |                                       |
    | 本线程顺序                            |
    v                                       v
ready.store(true, release) --同步--> ready.load(acquire) 读到 true
                                            |
                                            | 本线程顺序
                                            v
                                        读取 data

传递得到：写入 data happens-before 读取 data
```

happens-before 是 C++ 内存模型中的先行关系，用于证明访问之间的顺序和可见性，不是拿时钟比较谁先执行。通过这条关系，普通 data 的写和读得到正确排序，因此没有数据竞争。

### 3. 为什么 relaxed 不够

把示例的 store 和 load 都改成 relaxed，只保证 ready 自己的原子访问和该原子对象的修改顺序，不建立上述同步关系。data 的普通写入和读取没有 happens-before 关系，构成数据竞争，属于未定义行为。

- 不能只说“可能读到旧值 0，也可能读到 42”，因为有数据竞争的程序不能用这两个结果穷尽其行为。
- 在某台机器上运行很多次都是 42，也不是正确性证明。编译器优化和不同硬件的内存模型都可能影响表现。
- 如果把 data 也改成 atomic，并全部使用 relaxed，可以消除这个例子中对 data 的数据竞争，但仍不能仅凭 ready 为 true 就保证读到 data 的新值：跨变量的发布关系仍未建立。
- 如果消费者是在主线程确认 producer.join() 返回以后才启动，那么 join 等其他同步关系会改变分析。不能只看某行用了 relaxed，要看整个程序是否还有其他同步路径。

relaxed 适合只要求原子更新的独立统计计数，例如请求次数，不拿计数值作为访问其他普通共享数据的许可。在线程全部 join 后汇总计数，join 也提供了所需的完成同步。

### 4. 常见选项与使用位置

| 顺序 | 常用位置 | 保证与用途 |
| --- | --- | --- |
| memory_order_relaxed | load、store、原子读改写 | 保留原子性及该原子对象的修改顺序，不提供数据发布同步 |
| memory_order_release | store、原子读改写 | 发布此前的写入，供匹配的 acquire 接收 |
| memory_order_acquire | load、原子读改写 | 读取到对应发布值时，接收此前写入，供后续访问使用 |
| memory_order_acq_rel | 原子读改写，如 exchange、fetch_add | 同一操作同时具有 acquire 和 release 语义 |
| memory_order_seq_cst | load、store、原子读改写，默认值 | 具有相应 acquire/release 语义，并为 seq_cst 操作建立符合标准约束的单一总序 |

- 普通 store 不使用 acquire 或 acq_rel，普通 load 不使用 release 或 acq_rel；acq_rel 用于同时读和写的原子操作，而不是“随便加到哪里都更强”。
- C++11/14/17 还定义了基于依赖排序的 memory_order_consume，本轮不将它作为实用方案，先掌握 acquire，避免混入依赖传播的复杂规则。
- compare_exchange 的成功和失败可以分别指定顺序，失败路径是读取，不能使用 release 或 acq_rel；具体约束与算法应另行学习，不凭表格随意组合。
- 默认 count.load()、count.store(x)、count.fetch_add(1) 使用 seq_cst。先写出正确实现，有证据表明需要优化时再减弱顺序。

### 5. seq_cst 比 release/acquire 多什么

release/acquire 的重点是具体发布与接收之间建立同步。seq_cst 额外约束所有 seq_cst 操作在一个共同总序中的位置，便于推理跨多个原子变量的操作。

例如 x、y 为初值 0 的原子变量，线程一执行 x.store(1) 后读取 y，线程二执行 y.store(1) 后读取 x：

```text
线程一                       线程二
x.store(1, seq_cst)           y.store(1, seq_cst)
r1 = y.load(seq_cst)          r2 = x.load(seq_cst)
```

在没有其他写入的这个例子中，全用 seq_cst 时不能出现 r1、r2 同时为 0。若 store 用 release、load 用 acquire，则允许同时为 0：这时两次读取都没读到对方发布的 1，未建立相应同步关系。应在线程完成后观察各自的局部结果。

这不意味着 seq_cst 把所有线程、所有普通代码串行执行，也不意味着能修复任意普通变量的数据竞争，更不意味着 load+store 自动变成一个原子事务。

### 6. 与 mutex、缓存和 volatile 的联系

- mutex 的 unlock 与随后取得同一互斥量的 lock 建立同步。互斥锁既提供互斥，又让前一持锁线程的写入对后一持锁线程可见。
- release/acquire 不提供临界区互斥。发布完成后生产者若继续修改 data，消费者同时读取，仍可能产生数据竞争；重复交付需要完整的协议、队列或锁。
- acquire 不表示立即读取最新值；即使使用 seq_cst，消费者也可能先读到 false 再继续等待。例子的保证是“读到对应 true 后，随后可安全读取 data”。
- 不要把 release 解释成“把所有缓存刷到 RAM”，也不要把 acquire 解释成“每次从 RAM 重读全部数据”。编译器按目标硬件生成满足语义的代码，有时需要屏障，有时已有指令及硬件排序就足够。
- volatile 不提供跨线程同步，不能替代 atomic、mutex 或 memory_order。
- 调试器手动切换线程和一次运行输出不能证明内存模型正确性；测试可以暴露问题，正确性仍需依据原子操作、同步和生命周期关系推理。

### 7. 面试 30 秒版与理解检查

memory_order 用来规定原子操作的内存顺序。relaxed 只要求原子性，不用来发布其他数据；生产者用 release 发布标志，消费者用 acquire 读到该发布值后，两者建立同步，使发布之前的数据写入先行于接收之后的读取。seq_cst 是默认顺序，还为 seq_cst 操作提供单一总序。原子性不等于一组操作原子，也不等于周围普通数据自动线程安全。

- 问：ready 是 atomic，但全部使用 relaxed，能否安全发布普通 int data？
- 答：仅靠它不能。没有其他同步路径时，data 的跨线程读写存在数据竞争；需要匹配的 release/acquire、互斥锁或其他有效同步机制。
- 问：release/acquire 配对后，可以随时继续写 data 吗？
- 答：不能。它保证匹配发布之前的写入与接收之后的读取有序，不保护之后发生的任意并发修改。

## CPU 缓存行与伪共享（False Sharing）

### 原理与面试回答

- CPU 缓存以缓存行（cache line）为单位组织，常见缓存行大小为 64 字节，但具体取决于硬件，不能当成 C++ 标准保证。
- 伪共享：不同核心上的线程频繁修改不同变量，但这些变量位于同一缓存行。缓存一致性通常以缓存行为粒度维护，各核心会争夺该行的写入权限，产生失效、传输等额外开销。
- “伪”指业务上没有共享同一个变量，硬件层面却共享同一缓存行。通常需要至少一方写入，纯只读访问不会产生这种写入争用。
- 面试 30 秒版：伪共享是多个线程访问不同数据，却因为数据落在同一缓存行而产生缓存一致性竞争的性能问题。即使使用 atomic、没有数据竞争，也可能发生。可以通过缓存行隔离、线程私有计数后汇总、减少共享写入频率优化，但应在目标硬件上测量，权衡额外空间和缓存利用率。

### 原子变量也可能伪共享

```cpp
#include <atomic>

struct Counters {
    std::atomic<int> a{0};
    std::atomic<int> b{0};
};

Counters counters;

// 线程一反复执行：
// counters.a.fetch_add(1, std::memory_order_relaxed);
// 线程二反复执行：
// counters.b.fetch_add(1, std::memory_order_relaxed);
```

```text
同一缓存行：[a][b][其他字节...]
             ^  ^
           核心1 核心2
```

- 两个原子操作可以完全正确，但相邻的 a、b 可能位于同一缓存行，不能保证没有伪共享。
- relaxed 减少内存顺序约束，不会取消原子性或缓存一致性需求，因此不能消除伪共享。
- 伪共享不等于每次写入都回写 RAM；争用主要涉及缓存一致性协议和缓存行所有权转移。

| 概念 | 问题本质 | 结果 |
| --- | --- | --- |
| 数据竞争 | 不同线程对同一内存位置存在未被适当同步排序的冲突访问，至少一次写入，且至少一次非原子 | C++ 未定义行为 |
| 伪共享 | 不同数据位于同一缓存行，多核心访问发生写入争用 | 主要是性能下降，程序可以完全正确 |

### 如何缓解

下面假设已确认目标硬件缓存行为 64 字节，并且编译器、分配方式支持所需的过度对齐：

```cpp
struct alignas(64) Counter {
    std::atomic<int> value{0};
};

struct SeparatedCounters {
    Counter a;
    Counter b;
};

static_assert(alignof(Counter) >= 64);
static_assert(sizeof(Counter) % 64 == 0);
```

- 对 Counter 类型设置对齐，使它的大小也是对齐要求的整数倍，两个成员从不同的 64 字节边界开始。只给整个 SeparatedCounters 对象对齐，不会自动分开内部两个相邻的小成员。
- C++17 提供 std::hardware_destructive_interference_size（头文件 <new>），在标准库支持时可用于表达避免破坏性干扰的推荐间距；它是实现提供的值，不是运行时探测结果，对外 ABI 中使用还需注意构建配置一致性。
- 也可让每个线程在局部变量中累计，结束后再汇总，减少热路径上的共享写入；持续发布的线程私有槽位仍需留意是否共处一条缓存行。
- 空间隔离会增加对象大小，不要给所有成员盲目填充。应比较相同工作量、Release 优化下的布局变体，重复测量并核对结果，必要时结合硬件性能计数器定位；本节代码是机制示例，未进行性能实测。

### 本轮问答与易错点

- 问：两个线程分别修改不同的 std::atomic<int>，能保证没有伪共享吗？
- 答：不能。atomic 解决相应访问的原子性等正确性问题，不能保证两个变量位于不同缓存行；若它们共享缓存行并被不同核心频繁写入，仍可能发生伪共享。
- 注意：不把“线程安全”等同于“性能好”，不把“不同变量”等同于“不同缓存行”，也不把 alignas(64) 当作跨所有硬件的万能方案。

## 碰撞检测

- 碰撞检测 四叉树KDtree
- AABB 、OBB有向包围盒
- SAT分离轴定理
- 如果两个物体不发生碰撞，则一定存在一条直线，能将两个物体分离，这条能够隔开两个物体的线称为分离轴。可以假想有一束平行光从不同的角度照射待检测的两个多边形，当有一个合适的角度使得两者的影子没有重叠（投影的幕布于光线垂直），那么分离轴就找到了。
- 但实际中，我们不需要这么麻烦，只需要依次在多边形的每个边做投影即可。对于两个矩形的检测最多需要进行四次投影即可
- GJK 闵可夫斯基差
- 主要思想：当两个图形（凸多边形）发生重叠时，那么在两个图形中一定存在一对点，相减后为原点。
- 之后，我们取与起始向量垂直的向量作为新的方向向量，值得注意的是，这样的方向向量有两个，一个是 指向原点的v，一个是 背离原点的u
- 从以上几个步骤，不难看出， GJK 是一种 迭代算法，它需要不断地检测单纯形是否包含原点。它退出迭代的条件是：
- 单纯形包含原点
- 单纯形最后添加的顶点与搜寻方向点乘小于0
- 游戏里先 broad phase 再 narrow phase：四叉树/KDTree/BVH/AABB 先筛候选，再用 SAT/GJK/射线等做精确判断，别一上来全量两两检测
- 离散帧碰撞容易穿透：角色下落速度快或浮点误差时，只看当前帧位置不够；可以记录上一帧脚底位置和当前速度，只在“上一帧在平台上方、本帧穿过平台高度”时修正 y 坐标和速度

## 图形学与游戏客户端临场点

- 欧拉角：yaw/pitch/roll 直观，适合编辑器面板和人工输入；缺点是旋转顺序相关、可能万向锁、连续插值容易绕远路或抖动
- 四元数：单位四元数表示 3D 旋转，本质是绕某个单位轴旋转一个角度；适合相机、Actor transform、骨骼动画的组合旋转和插值
- 四元数注意归一化；`q` 和 `-q` 表示同一个旋转，做 slerp 时要选夹角更短的一侧
- 工程取舍：编辑器外显可以用欧拉角，内部姿态/动画插值用四元数，送渲染管线或做坐标变换时通常转成旋转矩阵参与 Model/View 矩阵计算
- 主循环：每帧处理输入、算 delta time、update 当前场景、draw，再按目标 FPS sleep；移动、动画、技能 CD、无敌帧、BUFF、道具刷新都要用 delta/Timer 驱动，避免不同机器帧率影响速度
- 主线程/渲染线程/工作线程：UI 和场景对象通常只能在主线程或引擎规定线程修改；后台线程只做加载、计算、解析，结果通过队列/任务切回主线程应用
- 2D 截图/CV 只能给候选，不等于 3D 行动权威；稳定链路是候选 → 射线/grounding → 平面确认 → 规划执行 → postcheck
- 深度、法线、表面身份分别解决“远近关系、朝向/平面、是不是同一目标面”的问题；最终世界坐标要由引擎几何和射线确认，不能只靠图片猜
