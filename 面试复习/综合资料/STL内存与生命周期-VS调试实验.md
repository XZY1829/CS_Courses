# STL 内存与生命周期：VS 调试实验

配套代码：[stl-observe.cpp](stl-observe.cpp)。实验使用 C++17（代码本身可用 C++11 编译），先观察 vector，再把方法迁移到其他容器。内部成员名、对象大小、容量增长和事件顺序依赖标准库及构建配置，不把一次调试结果当成标准保证。

## 1. 实验目标与 VS 配置

- 在独立的 C++ 控制台项目中使用配套文件作为唯一包含 main 的源文件，避免与原来的 main 重复链接。
- 选择 Debug / x64，关闭优化（/Od），生成调试信息（/Zi 或 /ZI）。标准版本选 C++17 即可。
- 先保留常规 MSVC Debug 迭代器检查配置；观察对象布局时记下 _ITERATOR_DEBUG_LEVEL，不能跨 Debug/Release 沿用偏移。
- 首轮不进入标准库内部：看日志和容器前后状态。第二轮再对已明确的一次操作逐语句进入源码。
- 实验中的 Trace 包含 id、value 两个 int。id 用于区分对象身份；构造创建新 id，赋值保留目标 id。移动时将源 value 设为 -1 是本实验主动设计的行为，并非 C++ 对移动后对象的统一要求。
- 日志增加了可观察副作用，适合观察语义，不适合测量性能；不要据此推断 vector<int> 的机器指令或拷贝耗时。

## 2. 首轮断点怎么打

在 checkpoint 函数内带 BREAKPOINT 注释的下一行打断点。每次命中时，对应 vector 操作已完成，临时实参也已经结束完整表达式生命周期。

按 F5 到下一个 checkpoint，先比较地址、size、capacity 和已经输出的事件；F10 用来跳过函数调用，F11 用来进入当前调用，Shift+F11 跳出。黄色箭头通常指向下一条将执行的语句，而不是已经执行完的语句。

| 阶段 | 操作 | 主要观察 |
| --- | --- | --- |
| 0 | 空 vector | size 为 0；容器对象已存在，但没有 Trace 元素 |
| 1 | reserve(2) | 容量至少 2，size 仍为 0，没有 Trace 构造事件 |
| 2 | emplace_back(10) | 容量充足，直接构造一个元素 |
| 3 | push_back(Trace(20)) | 构造临时对象、移动构造新元素、析构临时对象 |
| 4 | reserve(capacity()+1) | 必然重新分配；新元素构造，旧元素析构，容器本身地址不变 |
| 5 | reserve(8) | 只调整容量，元素仍然只有两个；必要时转移已有元素 |
| 6 | resize(8, fill) | 已有足够容量，新增六个值为 7 的元素，来自 const 引用填充值的拷贝构造 |
| 7 | erase(begin()+1) | 后续元素向前移动赋值，尾部多余对象被析构；元素数量减少 |
| 8 | clear() | 元素全部析构，size 为 0，capacity 保留 |
| 9 | emplace_back(99) | 复用保留存储；相同地址上可能构造出新的对象身份 |

erase 中“逻辑删除某个值”不等于“这个地址处的对象一定立刻析构”：常见实现先向前移动赋值，最后析构尾部对象。id 日志能帮助区分赋值和构造。不要假定新旧对象转移、日志的所有细节顺序跨实现一致。

## 3. 监视窗口与两份内存视图

在 checkpoint 内，v 是原容器的 const 引用，因此 &v 仍是原 vector 对象地址。在监视窗口添加：

```cpp
phase
&v
v.data()
v.size()
v.capacity()
sizeof(v)
sizeof(Trace)
```

仅在 v 非空时再查看 &v[0]、v[0].id、v[0].value。如果 VS 不能求值某个函数表达式，可使用 checkpoint 打印的值，或展开 v 的原始视图。

### 内存窗口一：&v

查看容器管理信息，不是元素内容。MSVC 常见内部路径为 v._Mypair._Myval2，其中 _Myfirst 是元素起点，_Mylast 是已构造元素的尾后位置，_Myend 是容量尾后位置；迭代器调试模式还可能有 _Myproxy。

这些路径和偏移不是标准接口，以当前版本原始视图为准。不要把首个非零指针自动当作 vptr 或元素指针。

### 内存窗口二：v.data()

只有 size > 0 时把这部分当作已有元素解读。若 sizeof(Trace) == 8，且两个 int 各占 4 字节、按所示顺序布局，一个元素可读为：

```text
01 00 00 00  0a 00 00 00
id = 1       value = 10
```

下一个元素起点是当前起点加 sizeof(Trace)，不是固定认为所有 STL 元素都是 4 字节。十六进制两个数字是一个字节；内存窗口一行的显示宽度也不是元素边界。

重新分配后，每次重新求值 v.data()，不要继续盯着此前打印的旧地址。旧区域仍显示数字，只能说明字节暂时残留，不能证明旧对象还活着。

clear 后可以观察管理指针和容量；不能因为分配还保留就调用 v[0] 或把原元素当作有效对象。容量中未使用的空间也不是可通过下标访问的元素。

## 4. 第二轮观察拷贝与移动

在 Trace 的拷贝构造、移动构造、拷贝赋值、移动赋值、析构函数内分别打断点。每次命中看：

- this：目标对象地址。
- other（有此参数时）：源对象、源地址和 id。
- 调用堆栈：是谁触发这次操作，是 push_back、reserve、resize、erase 还是作用域退出。
- 断点是否停在操作之前：移动函数中执行 other.value = -1 前后，源对象状态不同。

默认移动构造是 noexcept。然后在 VS 项目属性的 C/C++ → 预处理器 → 预处理器定义中追加 TRACE_THROWING_MOVE（保留已有定义），重新生成，再比较阶段 4。

- 默认：已有元素可通过不抛异常的移动构造转移。
- 定义宏后：移动构造签名变成可能抛异常；拷贝可用时，常见实现为保持异常保证选择拷贝构造。
- 宏不会真的抛出异常，只改变异常规格；本实验没有验证异常回滚路径。
- push_back(Trace(20)) 在容量充足时仍会使用移动构造，即使移动没有 noexcept。不要把“扩容搬迁时可能优先拷贝”误解为“所有调用都禁用可能抛异常的移动”。

移动赋值也受同一个宏控制，实验重点比较的是扩容时的移动构造。第一次看懂后再研究 noexcept 与异常保证的完整边界。

## 5. 数据断点与进入 STL 源码

暂停后，在 VS 支持的本机 C++ 调试环境中使用“调试 → 新建断点 → 数据断点”，或右键原始成员选择值变化时中断（具体入口随版本不同）。

- 监视某个已有元素的 value 地址、长度 sizeof(int)：适合追踪谁写入该字段，但元素重新分配后旧地址断点不再代表它，需要重设。
- 监视 &v._Mypair._Myval2._Myfirst，长度为指针大小：若当前版本允许访问该原始成员，可在存储指针变化时停住，用调用堆栈找到扩容路径。
- 数据断点盯的是内存位置，不会自动跟随对象移动；硬件支持的数量、大小有限。

要进入 STL，在主函数的 v.reserve(v.capacity()+1) 处断住，按 F11。VS 可能因“仅我的代码”、单步过滤或缺失源码而跳过：可在调试选项中调整“启用仅我的代码”，并通过调用堆栈、打开编译器实际使用的 vector 头文件、在具体函数中下断点进行定位。只关闭“仅我的代码”不保证所有过滤都被取消。

优先跟踪三个阶段：分配新存储 → 在新地址构造/转移元素 → 销毁旧元素并释放旧存储。内部函数名随 STL 版本变化，不背名字。

## 6. 进一步实验的顺序

1. vector<int>：只看连续存储、地址、size、capacity，避免靠旧字节判断移动。
2. vector<Trace>：使用本实验观察构造与赋值的差别。
3. vector<unique_ptr<int>>：比较 &v[i]（智能指针元素地址）与 v[i].get()（其管理对象的地址）。扩容可改变前者，但移动所有权不会移动其管理的 int。
4. unordered_map<int, Trace>：记录有效元素地址，再强制增加桶数；观察 rehash 后元素引用和指针仍有效、旧迭代器失效，不使用旧迭代器验证。

默认先完成前两步，再探索其他容器。不要同时混入自定义 allocator、继承、多线程，否则很难判断日志来自哪一种机制。

## 7. 本次验证结果

- 本机使用 C:/msys64/ucrt64/bin/g++.exe，以 -std=c++17 -O0 -g -Wall -Wextra -pedantic 编译并运行两个版本，均退出码 0，所有断言通过，编译无告警。
- 默认 noexcept 版本在强制扩容阶段记录 move-construct；定义 TRACE_THROWING_MOVE 后，同一阶段记录 copy-construct。
- 两个版本均观察到 resize 新增六次填充值拷贝构造、erase 后移入元素的移动赋值、clear 析构全部元素但保留容量。
- 本次 GCC 环境中 sizeof(vector<Trace>) 为 24、sizeof(Trace) 为 8；不代表 MSVC Debug 的 vector 大小。未在 Visual Studio 中执行 GUI 调试或验证其实际对象偏移。
- 未进行性能测试，也未通过真实抛异常验证异常回滚行为。
